# 04 · 实体记录与组件

世界更新包中的实体列表是每个 tick 的可见实体快照：每个可见实体一条记录，
客户端按掩码增量覆盖本地实体池。本文给出记录外壳、句柄编码和每个组件位的
字段顺序。

> **2026-08 字段审计修订**：本文旧版把若干“参考服务端不发”当成“客户端无用”
> 的证据，这是不成立的。逐字段的客户端证据、已证伪条目和仍未闭合的点见
> [09-field-audit.md](09-field-audit.md)。本版已按该审计修正 `0x1/0x2/0x8/0x20/0x40/0x400/0x1000/0x2000/
> 0x4000/0x100000/0x200000/0x20000/0x40000/0x800000`，并补上 `flags` 的
> `0x04/0x20/0x40` 与增量索引表；并删除 `0x400000` 的 `u8 rarity`
> （客户端只读 collected/target/item）。

## 1. 记录外壳

```
LE u32  handle
u8      flags        线上值 = 逻辑值 XOR 0xac
LE24    mask         组件掩码，低位在前
fields...            按 mask 的位从低到高依次排列
```

| flags（线上） | 逻辑值 | 含义 |
| ---: | ---: | --- |
| `0xcc` | `0x60` | 普通实体（完整 mask + body） |
| `0xc4` | `0x68` | 装备扩展（花朵，含 16 槽与 8 回充） |
| `0xce` | `0x62` | 普通 + 新到达（bit 1） |
| `0xc6` | `0x6a` | 装备扩展 + 新到达 |

逻辑位定义（`$601` 397914–397944、398459、398491、407210）：

| 位 | 含义 |
| ---: | --- |
| `0x02` | 新到达；首帧位置直接设为目标 |
| `0x04` | **跳过 `$974` 初始化**；本条复用上一条的组件状态 |
| `0x08` | 装备扩展（16 槽 + 8 回充） |
| `0x20` | **完整 3 字节 mask 存在** |
| `0x40` | **实体 body 字段存在**；否则本条只有组件“存在性”变更 |

- 客户端读取时先 XOR `0xac`，再判断**逻辑值**的 bit 3（装备扩展）与 bit 1
  （新到达）（A/B，`$601` 397900–397930；服务端 `record()` 写
  `(equipment ? 0xc4 : 0xcc) | (arriving ? 2 : 0)`）。
- 注意方向：线上 `0xcc` 是普通、`0xc4` 是花朵；不要把表中的“线上/逻辑”两列
  再对调一次。旧版本曾把 `0x60/0x68` 写成线上值，导致花朵被当成普通实体。
- “新到达”只影响首次插值：客户端会把首帧位置直接设为目标位置；服务端用它标记
  新掉落物，避免从旧缓存位置飞入（A，`garden_projection.cpp`）。
- **`0x20` 是条件字段，不是恒定 3 字节。** 当 `flags & 0x20` 为 0 时，
  客户端不读 mask，而读一串增量编码的组件索引，以 `1` 结束：
  `index = prev + vu - 2`（`prev` 初始 0）。`$974` 917140–917229 与
  `$601` 432139 各有一个 24 目标 `br_table`。旧文档把 3 字节 mask 写成
  无条件字段，遇到 `0x00/0x08` 等记录会整体错位（A，见 09 §1.1）。

## 2. 句柄编码

```
handle = generation * 8192 + slot
slot   = handle & 0x1FFF          （13 位，0..8191）
gen    = handle >> 13             （19 位）
```

- 实体池：`world + 22848 + slot * 376`；实体对象 `+28` 存完整句柄（B，
  `wave/docs/client-20221030.md`）。
- 保留槽位：`1..5` 分别用于本地资料、玩家列表/小队、世界统计、场地、波次；
  普通实体从槽位 16 开始（A，W2）。
- 句柄复用必须递增代次；客户端用代次拒绝旧句柄的受击/掉落事件（A，W2）。
- `0` 句柄仅用于列表终止，不能作为实体。

## 3. 组件掩码

掩码是 24 位小端；**完整快照**时客户端按位升序读取，缺位即跳过。下表“字段”
列是该位存在时的字节顺序；“消费者”列给出使用该字段的函数。注意：body 的实际
门控是实体上的持久 presence 标志，不是本条 mask；只发增量位会错位，见 §3 末
的约束。

| `0x400000` | `u8 collected`、`vu target`、`vu item`（`$55` 打包读取；**无 rarity**） | 地面掉落；+12 target、+16 item 低 16 位 | 掉落渲染 | **R** |
| `0x800000` | 300 × `f64`、300 × NUL 字符串 | 300 项表；**构造/解析/析构之外无 load**，客户端确认无消费者 | 无 | **W** |

> 证据列沿用 [09-field-audit.md](09-field-audit.md) 的细分：**R** = 找到客户端
> 读取指令，**P** = 字段已解析但下游未闭合，**W** = 写入后全模块无读取。
> 三者都是 B 级静态证据的子类；不再使用“服务端不发”作为 C 级证据。

### 字段顺序示例

一个非花朵实体（掩码 `0x1|0x400|0x1000|0x80000`）的 body：

```
00                    # 0x1
00 00                 # 0x400 heading = 0
<x f32> <y f32>       # 0x400
<radius f32>          # 0x1000
<generic flags u8>    # 0x80000
```

花朵还会在 `0x1` 之后插入 `0x20`（4 字节 + 16 槽 + 8 回充）和 `0x100`
（昵称），顺序仍按掩码升序；不能把上面的偏移直接套到花朵上。

字段不是“按组件块”排列，而是**所有置位组件的字段按掩码升序拼接**。因此不能用
固定偏移读取整个实体；必须逐位解析。

> **持久 presence 标志的约束**：`$601` 的 body 按实体上的持久标志
> （`entity+57` 的 bit1/2/3/4、`entity+59` 的符号位等）逐块读取，而不是只看
> 本条 mask；`$974` 在 mask 缺位时**不会清零**这些标志。因此一条带 body 的
> 记录必须为所有曾经置位的组件提供字段。最稳妥的做法是每次 body 都发完整
> mask（`0x20` 置位）并列出全部组件；只发“本 tick 变化的位”会让客户端从
> 第一个历史位开始错位（P，见 09 §1.2）。

## 4. 关键组件的细节

### 0x1 · 基础字节

```
u8 flags
```

- 固定 1 字节，写入 232 B 槽的 `+8`（`$589` 分配 29,696 B 池，`$601`
  398506–398579 读取，store 在 398545）。
- **不是 write-only。** `$1795` 在 1144862–1144871 读取
  `*(u8*)(*(i32*)(entity+64)+8) & 1`，把它作为 `select(1,0,...)` 的因子，
  参与渲染插值。`$2611` 第 23 行出现同构的 `(*(u8*)(*(i32*)($2+4))) & 1`
  选择文本锚点 `+20`/`+24`，提示同一位也用于文本路径（该函数参数结构未完全
  对齐，暂不作为独立证据）。因此 bit 0 = 渲染/插值开关（R）。其余 7 位未找到读者，但不能再说整字节无读者。
- 参考服务端恒写 0；这只说明服务端取值，不决定客户端是否有读者。

### 0x8 · world 统计表

```
11 × vu     # world+124..164（旧版少算 1 个）
10 × vu     # world+208..244
u8          # world+288
```

- world 级组件，不是普通实体字段；`$269` 初始化，`$601` 读取 **22** 个值
  （旧版写 21，漏了 `+164`）。
- `+292..+412` 的 10 个空 `std::string` 是客户端本地初始化，不是线上字段。
- 未找到对 world `+124..+288` 的明确读者；但 `+124` 这类小偏移在多个结构里
  复用，不能据此判 W。既不能用“服务端只发 count + 61 个 0”来证明，也不能
  写成“客户端已确认无用”。等级 P（见 09 §3.4）。

### 0x2 / 0x4 / 0x40 / 0x800000

- `0x2`：`u8` + NUL 字符串 + **`vu`**，写入标签结构 `world+52` 的 `+60/+64/+76`；
  旧版漏了末尾的 `vu`，会让后续组件整体错位。字段完整解析，但下游消费者尚未
  闭合（P）。“参考服务端不发”不再是删除该段的理由。
- `0x4`：2 × `LE32` 句柄。每个句柄先经 `$201` 查 handle→指针映射
  （`world+22324` 的表），再由 `$601` 399800 附近插入 `entity+144` 的侵入式
  链表（节点字段 `+152/+156/+160`）。目前只证明“插入”和析构时的 unlink，
  没有找到遍历者（P）。
- `0x40`：**空载荷**；`$969` 分配 **8 B** 节点（`+0=entity`、`+4=timestamp`），
  存到实体 `+72` 并追加到 world `+624` 的指针向量；`$601` 不读取任何字节。
  旧文档“12 B 节点 / world+592”是错的。是纯 presence 位，但节点消费者尚未
  闭合（P）。
- `0x800000`：300 × `f64` + 300 × NUL 字符串，`world+3088/+6688`。**客户端
  确认无消费者**：除了构造（428034）、解析（428041/428318）、增量重初始化
  （432818/435939）和析构（946940）之外，全模块没有任何以 `+3088/+6688`
  为基址的 load。等级 W（见 09 §3.7）。它仍可能被服务端发送，只是客户端白读。

### 0x20 · 花朵状态与装备

```
u8 a, u8 b, u8 level, u8 d
if (记录 flags 的 bit 3 / 0xc4 置位):
  16 × vu packed      # 低 8 位 = type，高 8 位 = rarity
  8 × vu reload       # 0..65535，0 = 破碎，65535 = 就绪
```

- **16 个槽各是一个打包 varint，不是“type varint + 独立 rarity 字节”。**
  `$601` 407218–407383 连续 16 次 `$55`，每次只读一个 varint 并截断为 u16
  存到 `+12,+14,...,+42`；`$998` 第 17 行用 `value & 0xFF` 取 type、
  `value >> 8` 取 rarity。旧字段表会让解析器在第一个非零槽后多读 1 字节，
  从那里开始整体错位（R）。
- 前 8 槽为主槽，后 8 槽为副槽（本地映射，W3 使用 6/7/8 槽解锁）。
- `reload` 是**归一化比例**，不是毫秒：客户端 `$126/$998` 做 u16/65535 后
  插值绘制扇形（A）。
- 等级/槽数判定使用第三字节；默认等级 1（`$140`）。
- 16 槽与 8 回充是否存在的开关是**记录外壳的 flags bit 3**（`0xc4`），不是
  组件内的某个 bit；花朵记录必须置该位，否则客户端会把槽位字节误读成昵称。

### 0x200 · 小队 roster

客户端 `$601` / `$182` 的实际读取顺序（B）：

```
4 × NUL 字符串       # 成员名 → roster +8/+20/+32/+44
4 个 ready bit       # 位打包，写入 roster +72
4 × NUL 字符串       # → +76/+88/+100/+112（成员标签/宠物名）
4 × LE32 句柄        # 分别插入 +140/+152/+164/+176 的四个 set
4 × LE32             # → +216/+220/+224/+228
64 × vu16            # → +248..+374（4 成员 × 16 装备槽）
f32                  # → +632
4 × u8               # → +636..+639
```

- 房间码是**单个** NUL 字符串，写入 roster `+204`；它不在上述 4 字符串组里。
- ready 状态是**1 字节里的 4 个位**；服务端发 4 个独立字节时，只有第一字节的
  bit0..bit3 被消费，后 3 字节是死字节（B/C）。
- `+204` 之后的 488 字节是对象构造时的清零区，不是线上“84 B 默认块”。
- 服务端 `garden_projection.cpp` 目前发的是“4 名 + 21 个 0 + 房间码 + 84 个 0 +
  4 字节”。它只能保证 4 个名字和 ready 位落在客户端前 17 字节内；按客户端的字段顺序，
  房间码不会落在 `+204` 的字符串字段，而会落进后面的整数区。参考服务端的房间码
  实际由 URL hash 提供，而不是 0x200；这一点需动态抓包再确认（B/C）。
- 旧文档的“21 B 默认 + 房间码 + 84 B 默认 + 4 × 席位标志”是服务端投影的
  字节外形，不是客户端的字段 schema；不要再按它推断准备状态或库存。

### 0x800 · 波次与目录

```
u8   first     # 红色清场条（0..255）
vu   wave      # W1.number - 1
vu   biome
216 × vu       # 目录计数，index = type * 6 + rarity
u8   last      # 蓝色刷怪条（0..255）
```

- 36 类型 × 6 稀有度 = 216 项（A）。
- `first/last` 位于 world `+820/+2560`，由 `$828` 绘制两条归一化进度（A）。
- 顺序：蓝条先推进（刷怪），红条在刷怪结束后推进（清场）（A，用户确认）。

### 0x2000 · 场地

```
f32 radius     # 圆形场地半径
u8 r, g, b     # 背景色
```

- 只发给场地实体（句柄 8196），**不要**给每个实体发（A）。
- 半径参与本地控制约束；颜色全屏填充（A）。

### 0x80000 · 通用渲染与受击

```
u8 flags       # bit 0 = 死亡膨胀/淡出（线上只有这 1 字节）
```

事件向量不在 0x80000 的 wire 里：它是客户端本地容器，由 S→C 32 向其中
追加 24 B/条（`$988`）。`$601` 的 0x80000 分支只读 1 字节（426900–426974）。

- `$597` 从首次绘制计时 150 ms：alpha 1→0，比例 1→2（A）。
- `$51` 消费受击事件，绘制约 150 ms 闪白/红（A）。

### 0x400000 · 掉落物

```
u8  collected    # 1 = 被拾取，播放缩小旋转
vu  target       # 飞向的实体句柄，0 = 原地
vu  item         # 物品类型（客户端截成 u16 存 +16）
```

**没有 `u8 rarity`**：`$601` 427359–428026 只读这三项，`+8` 是
collected，`+12` 是 target，`+16` 是 item 的低 16 位；随后直接进入
0x800000 分支。旧文档的 rarity 不是客户端 wire 字段（来源未在客户端找到）。

- 与 `0x400/0x1000/0x80000/0x1` 组合使用；服务端投影的 mask 为
  `1 | 0x400 | 0x1000 | 0x80000 | 0x400000`（A）。

## 5. 删除与保留

- 删除段在实体列表之前，按句柄删除；删除后的槽位在淡出保留期内不能复用。
- 服务端对“已见实体”保留 400 ms 的死亡记录：设置 `0x80000` bit 0 后再真正
  删除（A）。
- 客户端不补造未见实体的死亡动画（A）。
- 重生使用新句柄/新代次，不复用旧控制对象（A）。

## 6. 解析伪代码

```python
def read_entity(buf, p):
    handle = le32(buf, p); p += 4
    if handle == 0: return None, p
    flags = buf[p] ^ 0xac; p += 1
    mask = buf[p] | buf[p+1]<<8 | buf[p+2]<<16; p += 3
    body = {}
    for bit in range(24):
        if not mask & (1 << bit): continue
        body[bit] = COMPONENTS[bit] (buf, p)  # 返回 (value, new_p)
        p = body[bit][1]
    return Entity(handle, flags, body), p
```

组件读取器必须严格按上表顺序实现；任何一位解析错位都会连锁破坏后续实体和命令
列表。
