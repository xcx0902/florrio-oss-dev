# W3 SQLite economy and recovery — 2022-10-30

Implementation: `server/store/store.hpp`, `server/store/store.cpp`.
Native acceptance: `tests/native/w3_store.cpp`, no arguments.
Rules identity: `20221030.store-reconstruction.1`.

## Public boundary and profile lifecycle

The public C++20 types are independent of simulation and wire structs. The
implementation consumes the generated dated catalog inline for the single
authority on level thresholds, slot unlocks, and craft success probabilities.
Stock `find_package(SQLite3 REQUIRED)` / `SQLite::SQLite3` supplies SQLite;
no additional database package or catalog library linkage is required.

`Store(path, options)` opens/migrates the database. `create_guest()` creates a
new identity; `recover_guest(token)` only looks up an existing one and returns
an optional. `admit(claimed_token)` recovers an existing valid bearer or mints an
unrelated fresh identity. An unknown claimed token is never adopted. The
database issues 256-bit opaque credentials from `/dev/urandom`, encoded as
exactly 64 lowercase hexadecimal characters. Guest IDs are server-generated
positive SQLite integer IDs. Craft RNG injection cannot influence credentials.

Profiles persist guest ID/token, cumulative XP, highest completed wave, level,
owned quantities, 16 equipment slots, explicit mob gallery discoveries, and a
monotonic version. Owned quantities include equipped items. Production guests
start at XP 0, highest wave 0, level 1, version 0, with exactly five Common
Basic petals in main slots 0–4. There are no other starter grants, and the
initial mob gallery is empty.

`Options::allow_test_seed` defaults to false. Only an explicitly enabled
`seed_for_testing(token, TestSeed)` can replace an offline fixture profile.
Seeding increments version and does not implicitly add gallery discoveries.
Production protocol code must not expose that helper as an endpoint.

Equipment slots use a fixed internal layout: main `[0,8)` and reserve `[8,16)`.
An optional item represents one equipped copy. The same item can occupy several
slots only if ownership covers all copies. Owned items use original petal
kind IDs 1–45 and rarity 0–5. Gallery entries use the separate original **mob**
kind IDs 1–35 and rarity 0–5. Petal ownership, crafting, pickup grants, and
fixture inventory never implicitly modify mob discoveries. Callers supply
`Reward::discoveries` or `TestSeed::discoveries` explicitly.

Original cache equipment uses a compact boundary tied to current slot count;
the wire/cache adapter owns translation to/from the fixed store layout.
Static evidence: `$70` clears indexes at or beyond `2 * cached_num_petals`,
and `$237` reads reserve index `index + cached_num_petals`. Store code does
not accept cache blobs as authoritative inventory. Guest credentials, match
recovery state, and presentation caches have separate lifecycles. Only the
profile and its economic journals live in this database.

## Schema and migrations

Opening a fresh database applies v1 and v2 in a single `BEGIN IMMEDIATE`
transaction. Existing v1 is upgraded without replacing profile data. A
`PRAGMA user_version` greater than 2 is rejected. Opening is idempotent.

| Version | Table             | Durable data / primary identity                                                     |
| ------- | ----------------- | ----------------------------------------------------------------------------------- |
| 1       | `profiles`        | ID, unique opaque token, XP, highest wave, level, version                           |
| 1       | `inventory`       | Positive owned count, keyed by `(guest_id,kind,rarity)`                             |
| 1       | `slots`           | Occupied slot only, keyed by `(guest_id,slot)`; range 0–15                          |
| 1       | `discoveries`     | Explicit mob gallery membership `(guest_id,kind,rarity)`                            |
| 2       | `command_results` | Complete semantic fingerprint + result, keyed by `(guest_id,scope,command_key)`     |
| 2       | `reward_results`  | Complete semantic fingerprint + shared result, keyed by `(match_id,scope,event_id)` |

All profile child tables and command journals reference a profile with foreign
keys enabled. The database uses WAL and `synchronous=FULL`; file databases
must successfully enter WAL. The explicit `:memory:` SQLite mode is accepted
for callers that do not need persistence. Inventory zeroes are omitted rather
than stored. Counts, XP and versions are restricted to SQLite's nonnegative
signed 64-bit range, `0..9223372036854775807`; arithmetic checks precede writes.
Highest wave is an unsigned 32-bit value. `reward()` only raises it.

## Commands, rewards, and transaction semantics

`equip(token, Command, EquipRequest)` validates a complete desired slot array,
current ownership, unlocked pairs, and the application-supplied authoritative
life eligibility. Equip preserves total ownership. The application must derive
`EquipRequest::alive`; it must not trust a raw client boolean.

`craft(token, Command, CraftRequest)` reserves equipped copies and `keep`
additional unequipped copies. At least five unreserved copies are required
for every roll. Success consumes five and creates one next-rarity copy of the
same petal kind. Failure consumes 1–4 and creates none. `CraftSummary` records
attempts, successes, consumed inputs, and returned/unconsumed inputs from the
submitted sets of five. A failed roll still has command status `ok`.

The original wire keep field may already include equipment; conversion to the
store's **additional unequipped keep** belongs to the application. `automatic`
maps the original all flag. Automatic mode stops when stock cannot fund another
five-input attempt; it never exceeds the requested cap. Manual batches either
complete the requested attempt count or commit no inventory changes. Both
operate on a single input tier and do not cascade through the outputs.

`Command{scope,key,expected_version}` uses server-defined scope and key. For
the original protocol, a connection UUID plus reliable sequence can establish
the replay boundary without a client-supplied command ID. Store checks the
token, then a prior journal result, then expected profile version. A matching
retry returns the original status, craft totals, and exact committed profile
without rerolling. This check precedes CAS so a lost reply can be retried with
the original expected version.

Fingerprints contain the full canonical request rather than a hash: operation,
expected version, item, policy flags, keep/caps, or desired slots/life eligibility.
They use a length-delimited little-endian encoding with no delimiter ambiguity.
Changing any semantic field under an existing scoped key returns `key_conflict`.
Result encoding has an explicit codec version, checked bounds, and no C++ ABI
or platform-dependent struct layout.

The inventory/progression mutation, version increment, and result insert commit
atomically in one transaction. Terminal command rejections are journaled with
unchanged profile/version so later restocking does not change their replay.
Unknown guest, invalid key, and version conflict are not journaled. SQLite
errors throw `store::Error` exposing its SQLite error code. Uncommitted reward
validation/CAS failures also leave no journal claim. A failed write can retry
the same original request after the external condition is resolved.

`reward(RewardEvent)` takes trusted match/scope/event identity plus the complete
server-eligible recipient set. The application determines player attribution,
shared eligibility, pickup distance, and logical segmented-death identity.
Use separate scopes for kill XP, pickup claims, and wave completion. A sorted
canonical recipient set settles atomically across all profiles; reordering the
same recipients replays. Repeating a segmented parent's event cannot award XP
twice. Competing pickup recipients conflict on the same event key so only one
claim commits. Changed quantities, XP, discoveries, recipients, or expected
versions conflict with a previously committed reward fingerprint.

Replay snapshots can be older than the application's latest profile. Never
overwrite a newer cached profile with an older replay result; use
`recover_guest()` for the latest full authoritative state as needed. No result
is reported successful until SQLite commits. Journals are retained without an
automatic TTL, so committed keys must never be reused for a different action.

## Exact limits and queue boundary

| Boundary                                    | Limit / policy                                                                                              |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Guest token                                 | Exactly 64 lowercase hex characters; unknown tokens never claim a profile                                   |
| Command scope/key; reward match/scope/event | Each 1–256 bytes                                                                                            |
| Craft attempts                              | 1–1024 per command; excessive counts reject                                                                 |
| Shared recipients                           | 1–256 unique positive guest IDs                                                                             |
| Owned item keys                             | 45 kinds × six rarities = 270 possible entries                                                              |
| Mob gallery                                 | 35 kinds × six rarities = 210 possible memberships                                                          |
| Equipment                                   | 16 persisted slots, with at most eight main/reserve pairs                                                   |
| Unlocks                                     | Five pairs below level 15; six at 15; seven at 30; eight at 45                                              |
| Rarity                                      | Common 0 through Mythic 5; no Ultra output                                                                  |
| Craft protection                            | Common Basic forbidden; Unusual+ Basic allowed; configured output ceiling and all equipped copies protected |
| Integer economy                             | `0..INT64_MAX`; nonzero stored item counts                                                                  |
| SQLite busy wait                            | Default 5000 ms; configurable range 0–60000 ms                                                              |
| Invalid RNG source                          | At most 128 rejected words before `SQLITE_ABORT`                                                            |

The store is synchronous and serializes one instance with a mutex. Separate
connections/processes serialize writers with SQLite `BEGIN IMMEDIATE` and a
bounded busy wait. WAL readers can continue while another connection holds a
write reservation. The application owns the bounded asynchronous work queue,
queue-full response, completion ordering, and tick isolation. No store call
should run on the simulation tick; do not reenter a store from its callbacks.

## Dated evidence and explicit reconstructions

Original Wasm SHA-256:
`68094577a0ac1254fcffedbb46c0181d90893bd063e3eafa76489bba2776e7b0`.
Client build: `b632797f0ee487dd99df460b13bde6d7ce5c9773`.

Independent success rolls follow the existing `craft.rng.mode` evidence entry
in `data/evidence/20221030/rules.json` and the original 2022-10-20 changelog.
Importing legacy pseudorandom failure counters and maintaining their historical
transition-until-success mode is **unsupported**. New profiles never have such
counters. This implementation does not infer or import authoritative state
from the protocol's old craft-counter cache array.

Original `$902` reads display percentages from u32 memory `53136 + rarity*4`:
`[60,40,20,10,3,0]`; Common 60% was also confirmed through the original UI.
The generated catalog provides server thresholds
`[600000,400000,200000,100000,30000]` out of one million for Common through
Legendary inputs. Applying the display table as server success probabilities
is an explicit **server reconstruction assumption**. The store reads the
catalog table, avoiding an independently maintained numeric copy.

The original UI says failure destroys 1–4 petals. **Uniform** loss within that
range is inferred, implemented with a separate independent unbiased draw.
There is no claim that the original server's failure-loss distribution was
recovered. Success and loss use rejection sampling from uniform 32-bit words.
For success, words below 4294000000 are accepted and reduced modulo one
million; higher words are rejected. For four-way loss, all 32-bit words are
accepted. Fixture word `1000000` guarantees success; `1999999` guarantees
failure and, when reused for the loss draw, destroys four inputs. Word zero
is also a valid guaranteed success.

Original `$436` forbids `kind==1 && rarity==0` (Common Basic). Original `$107`
cached_num_petals through table 143 / `$3645` proves unlocks at levels
15, 30, and 45. The original inventory cache includes equipment (`$308`
subtracts equipped copies when calculating free craft stock).

XP thresholds remain the dated catalog's **reconstruction**, not recovered
historical server values. `store::level_for_xp` delegates to the exact same
catalog helper as projection. The catalog currently reconstructs quadratic
cumulative XP `100*(L-1)^2` and caps level at the client byte maximum 255;
the cap and its progress sentinel are read from the shared generated table.
Store does not maintain an independent XP formula or level cap.

## Verification and fault cases

`Options::fault` can throw at `after_inventory`, `before_commit`, and
`after_commit`. The first two roll back profile/version and journal together.
The last models a durable result with a lost reply; retry returns the original
committed result. Test child processes additionally `_exit` before and after
commit without running destructors or checkpointing, then reopen the real WAL
database and retry the original command.
