# Catalog semantics

## Inputs and owners

| Input                                        | Product owner                                                                              |
| -------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `schema/catalogs/rarities.json`              | ordered rarity indexes, symbols and names                                                  |
| `schema/catalogs/petals.json`                | petal symbol, identity, descriptions, rarity, recharge, slot count, label size/orbit flags |
| `schema/catalogs/petal-combat.json`          | draw/collision radius, damage, health, behavior + heal amount, orbit profile               |
| `schema/catalogs/entities.json`              | entity symbol, identity, scale, droppable petals, drop alias/weight, draw count            |
| `schema/catalogs/spawn-rules.json`           | weighted spawn bands                                                                       |
| `schema/catalogs/entity-spawn-defaults.json` | fixed spawn defaults and dynamic-formula flags                                             |
| `schema/catalogs/strings.json`               | names and descriptions                                                                     |
| `schema/catalogs/drop-rules.json`            | drop distribution constants                                                                |
| `schema/catalogs/state-flags.json`           | shared entity/world/activity/expression/input/variant bits                                 |
| `schema/catalogs/loadout.json`               | slot/instance capacities, unlock tiers and rarity experience                               |
| `schema/catalogs/gallery-overrides.json`     | display-only differences with a stated reason                                              |

`schema/catalogs/drop-chances.json` is generated by the pure derivation in
`tools/schema/drop-chances.mjs`; it is not an input. `tools/generate.mjs` validates
all owners and emits the C++/TypeScript views. Runtime code does not read JSON.

## Petals

39 records. `symbol` is the stable product name and generates
`catalog::PetalId` / `PetalId`; type id remains the uint16 catalog identity,
publishable in `0..255` because snapshots and loadout packets still carry one
byte. Ids may be sparse and array position is not an id. Display names are not
unique (`Rose` at 6/15/24, `Cactus` at 13/21/33, `Basic` at 1/35), so members
are disambiguated as `RoseUnusual`, `RoseEpic`, `RoseRare`, and so on.
`rarityIndex` indexes `rarities.json` and the petal drop-mass list. `labelFontSize` is the UI label unit, `drawRadius` is the
rendered card/art radius, and `collisionRadius` is the world collision radius.
They are separate fields; a zero collision radius is legal and is not replaced
with a silent default.

## Entity definitions

23 records. Entity ids use the same `0..255` publishable range and each row
has a stable `symbol` (`Rock`, `CentipedeHead`, `EvilCentipedeSegment`, ...).
`petalTypeIds` is the ordered drop pool; `dropAliasOf` inherits the canonical
root of another entity's pool (0 means none; alias chains are resolved to the
root and cycles are rejected); `dropWeight` is the species mass multiplier.
`dropDrawCount` is the number of catalog draw steps consumed before the
species initializer; it no longer carries the historical "component" name.
Unknown low-confidence offsets were deleted rather than renamed `opaque*`.

## Spawn rules

20 weighted records. Each names one entity and a list of spawn bands; band ids
must be inside `drop-rules.json:areaMix`.

## Drop derivation

`drop-rules.json` owns the unequal band areas, the six rarity masses, summoned
children, the reference species/mass and convergence thresholds. Derivation is
deterministic:

1. compute each species mass from `dropWeight` and children;
2. normalize against the reference species;
3. convert rarity masses to probabilities over the drop pool;
4. iterate child contributions until the configured saturation/iteration limit;
5. sort ascending by chance, then by petal type id.

The generated C++ table is read by `Catalog::drop_table`; the generated gallery
view is read by the menu. Neither path consults an archived tool at runtime.

## Petal combat

`petal-combat.json` holds only combat-owned values. Rarity, recharge and instance
counts are joined from `petals.json` during generation, so the two files cannot
drift. `PetalCombat` therefore has draw/collision radius, damage, health,
`behavior` (`Orbit` or `RoseHeal`), `healAmount` and `orbitProfile`. The former
the former numeric orbit-function chain is gone; `PetalBehavior` is the only
behavior selector and `healAmount` is the only heal parameter.

## Verification

```sh
npm run schema:generate
npm run schema:check
npm run test:integration
```

The native catalog test checks generated C++ values; the schema tests check
ownership, drops, transport and read-only `--check`; the integration test uses
real native bytes rather than an archived golden.
