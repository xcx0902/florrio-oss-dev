# Catalog semantics

## Inputs and owners

| Input | Product owner |
| --- | --- |
| `schema/catalogs/petals.json` | petal identity, descriptions, rarity, recharge, slot count, label font size, orbit flags |
| `schema/catalogs/petal-combat.json` | draw radius, collision radius, damage, health, orbit profile/function |
| `schema/catalogs/entities.json` | entity identity, scale, droppable petals, drop alias/weight, component draw count |
| `schema/catalogs/spawn-rules.json` | weighted spawn bands |
| `schema/catalogs/entity-spawn-defaults.json` | fixed spawn defaults and dynamic-formula flags |
| `schema/catalogs/strings.json` | names and descriptions |
| `schema/catalogs/drop-rules.json` | drop distribution constants |
| `schema/catalogs/gallery-overrides.json` | display-only differences with a stated reason |

`schema/catalogs/drop-chances.json` is generated by the pure derivation in
`tools/schema/drop-chances.mjs`; it is not an input. `tools/generate.mjs` validates
all owners and emits the C++/TypeScript views. Runtime code does not read JSON.

## Petals

39 records. Type id is the identity; display names are not unique (`Rose` at
6/15/24, `Cactus` at 13/21/33, `Basic` at 1/35). `rarityIndex` indexes the petal
drop-mass list. `labelFontSize` is the UI label unit, `drawRadius` is the
rendered card/art radius, and `collisionRadius` is the world collision radius.
They are separate fields; a zero collision radius is legal and is not replaced
with a silent default.

## Entity definitions

23 records. `petalTypeIds` is the ordered drop pool; `dropAliasOf` inherits
another entity's pool (0 means none); `dropWeight` is the species mass multiplier.
The low-confidence offsets were renamed only where the domain use is known;
unknown values remain documented opaque fields (`opaque100/104/108/110`).

## Spawn rules

20 weighted records. Each names one entity and a list of spawn bands; band ids
must be inside `drop-rules.json:areaMix`.

## Drop derivation

`drop-rules.json` owns the unequal band areas, the six rarity masses, summoned
children, the reference species/mass and convergence thresholds. Derivation is
deterministic:

1. compute each species mass from `dropWeight` and children;
2. normalize against the reference species;
3. convert rarity masses to probabilities over the drop pool;
4. iterate child contributions until the configured saturation/iteration limit;
5. sort ascending by chance, then by petal type id.

The generated C++ table is read by `Catalog::drop_table`; the generated gallery
view is read by the menu. Neither path consults an archived tool at runtime.

## Petal combat

`petal-combat.json` holds only combat-owned values. Rarity, recharge and instance
counts are joined from `petals.json` during generation, so the two files cannot
drift. `PetalCombat` therefore has draw/collision radius, damage, health,
orbit function and orbit profile.

## Verification

```sh
npm run schema:generate
npm run schema:check
npm run test:integration
```

The native catalog test checks generated C++ values; the schema tests check
ownership, drops, transport and read-only `--check`; the integration test uses
real native bytes rather than an archived golden.
