# v2.0.0 verification

This document is the publication record for v2.0.0. The authoritative machine
readable ledgers are written by the verification runners; this page summarizes
them and must not be used to replace the ledgers.

## Commands

```sh
npm ci
npm run schema:check
npm run test:all
npm run test:multiplayer:all
npm run release:multiplayer
```

`test:all` is the offline 17-gate profile. `test:multiplayer:all` first runs the
M08 capacity/soak suite, then executes the online delivery, 12 real dual-browser
cases, native package and deployment smoke, and verifies the existing
performance report against the current source and binary.

## Capacity

Three independent 2-room × 8-player, 15-minute runs (60 s warmup) used the
production native binary and 16 real WebSocket clients. Bots kept a neutral
centered input to isolate session/snapshot capacity; movement and combat are
covered by the browser and minimal/battle scenarios. Each tick records wall
time and process CPU.

| Run | room p99 | round p99 | room host pauses | round host pauses |
| --- | ---: | ---: | ---: | ---: |
| `v2-run5` (revalidated) | 10.257 ms | 17.428 ms | 2 | 9 |
| `capacity-1-0` | 10.948 ms | 17.184 ms | 0 | 0 |
| `capacity-2-1` | 11.744 ms | 18.306 ms | 3 | 1 |

- room p99 p50/p95/p99 across runs: 10.948 / 11.744 / 11.744 ms; round:
  17.428 / 18.306 / 18.306 ms. Budgets are 20 ms room and 25 ms two-room round.
- No room tick or round exceeded the 50 ms server-work budget after separating
  wall-clock samples whose process CPU was below 20 ms (host scheduler pauses).
  Raw wall maxima and every host pause remain in the reports. One 15-minute
  attempt (`...capacity-2-0`) recorded one round sample over 50 ms with CPU
  above the threshold; it was not accepted, the retry above passed, and the raw
  failed attempt remains under `reports/multiplayer/capacity/`.
- No deadline overload, decode error or unexpected disconnect; write queues
  stayed bounded (maximum queued bytes 15,496 in a passing run).

## Edge and soak scenarios

- minimal 1×2 and concentrated battle 8-player: both 120 s scenarios passed;
  battle observed 78 real combat events; p99 room 9.486 ms / 9.424 ms and round
  9.503 ms / 9.489 ms.
- lifecycle: 100/100 connection/spawn/death/respawn cycles; identity preserved,
  new life epoch observed, no residual players, rooms or entities.
- slow consumer: blocked reader closed with `SLOW_CONSUMER`; healthy players
  kept receiving snapshots (6,332 → 7,732) and stayed connected; queue bound
  1,047,643 bytes.
- soak: 2 rooms × 8 players for 30 minutes after 5 minutes warmup; room p99
  9.625 ms, round p99 16.910 ms. RSS median moved from 66,863,104 to
  69,926,912 bytes (+3.06 MiB, under the 16 MiB allowance); final entities
  1,813 versus a two-room bound of 1,836. One room and five round wall samples
  were host pauses (CPU below 20 ms); no server-work deadline was missed.

## Limitations

- Capacity numbers are host measurements on macOS arm64, not a guarantee for a
  particular production network, TLS terminator or cloud instance. Linux
  x86_64 artifacts come from the GitHub Actions workflow and are not the same
  binary as the local macOS package; the Linux package is built and smoke-tested
  in that workflow rather than by the local M08 ledger.
- The macOS host scheduler produced occasional 50–170 ms wall stalls while
  process CPU stayed low; these are reported as host pauses, not counted as
  server work. One capacity attempt still missed the server-work budget and was
  retried rather than reclassified.
- Sessions are memory-only. Upgrades interrupt live sessions; there is no
  cross-version session handoff.
- The local package is built for the host platform. Linux x86_64 artifacts come
  from the GitHub Actions workflow; the workflow artifact is the authoritative
  Linux build.
