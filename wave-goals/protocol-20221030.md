# 协议专项 · 驱动 2022-10-30 原客户端

**目标**　原版 JS/Wasm 通过本地服务发现和原二进制 WebSocket 交互，进入访客、大厅、对局和进度界面。通过真实客户端操作验证协议兼容。W0 已固定发现请求、原客户端发出的首个 socket 帧和合成回包的断开路径。历史成功回包、访客和对局消息从 W2 继续恢复。 [首包夹具](../wave/data/wire/20221030/bootstrap.json) · [W0 执行结果](00-baseline-and-evidence.md#w0-执行结果)

## P0 · 建立字节观测入口

1. 在 `wave/tools/reference/` 用本地发现响应和 mock socket 启动原客户端。按顺序记录启动、地区及服务器选择、访客身份、进入小队、准备、开局。记录每个 HTTP 路径、方法、结构和时序，以及 socket 创建、打开、首个发送、首个接收、关闭和重试。
2. 从 JS 胶水的发送、接收队列向 Wasm 消费点追踪。对每条消息登记方向、连接状态、长度、分帧、序号、整数编码、字段存在条件和客户端消费点。压缩、XOR、键和初始种子需由字节及代码流共同核实，再决定是否实现。
3. 建立测试捕获格式。每条记录保存顺序、相对时间、方向、原始长度、字节、可观察行为、来源和快照哈希。真实录制标 `captured`，根据读取器构造的标 `synthetic`，仅发送通路探针标 `transport-probe`。历史录制中的账号或凭证字段用测试替身替换并注明位置和语义。
4. 原版参考始终使用可控本地依赖。对发现、访客、登录返回和错误分别重放原客户端可消费的结构。只在字段有证据时从「候选」提升到「已验证」。无法推进时记录第一个期望字段或检查点。

## P1 · 按最短路径恢复格式

| 顺序 | 消息域                           | 第一条端到端证据                                      |
| ---- | -------------------------------- | ----------------------------------------------------- |
| 1    | 本地发现、服务器选择、访客       | 原版加载结束，菜单可操作，合法访客状态可见            |
| 2    | 握手、小队、准备、开始           | 原版能显示席位，发送真实准备请求，收到开局确认        |
| 3    | 首帧、实体、控制对象、移动输入   | 本地玩家和队友出现，可通过原客户端操作移动与攻击/防御 |
| 4    | 实体增删、波次、死亡、观战、重生 | HUD 跟随状态变化，旧实体删除，重生后控制权正确        |
| 5    | 库存、装备、合成、图鉴、结算     | 原版界面发出的操作被裁决，结果反馈与存档一致          |
| 6    | 公开匹配、重连、场景、蚁穴和 PvP | 两个客户端完成加入、恢复、切场、得分与回大厅          |

1. 为每一域先从最小已知数据构造合法样例，再单字段替换，观察是被拒绝、显示改变还是进入新状态。保留引起状态改变的最短样例及原客户端可观察结果。依据默认全量/增量假设的字段标为候选，直到独立夹具证实。
2. 将确认的消息编码为 `wave/data/wire/20221030/` 中的契约和黄金字节。为每个字段记录编码、条件、量化单位、状态约束和证据链接。利用记录的原版出站字节解码，并逐字节验证已确认的服务端编码。单纯通过自己的编码再解码不能替代原客户端验收。
3. 如线上行为只有一条旁证，先保留独立夹具并标明覆盖。原版能读到某个字段代表兼容性证据，字段在真实历史对局中的值由 [历史证据流程](00-baseline-and-evidence.md#003-建立历史规则表) 判定。

## P2 · 接到独立服务端

1. 在 `wave/server/wire/` 实现历史收发。该层有界解析并校验方向、长度、世代、状态、枚举和重复命令。生成协议内部动作，映射已有 `PlayerId`、对局、寿命及目录键。对局状态由应用层投影成各连接可见字节。内部房间和存档版本走服务端内部数据结构。
2. 在 `wave/web/` 将兼容壳与真实 socket 地址接到独立服务端。按原应用可接受的时序和结构回应。每次重连重新建立完整可见状态，实际发送方式按取证的原客户端协议执行。每个连接独立维护需要的基线、序列、可见实体和私有字段。
3. 把客户端菜单未提供的内部管理操作留在测试夹具。准备、移动、装备、合成、迟入、退队和重生应由真实原版输入或权威状态触发。发送错误消息时使用已确认的错误或关闭路径，并测试原版页面显示。
4. 用字节夹具检查编码、解码和异常输入。用真实原客户端连接新服务端，确认实际操作产生可处理的请求，权威状态和结果能被客户端读取。

## P3 · 执行验收

在独立 `wave/package.json` 注册 `test:wire`。夹具验证包括合法样例、截断、非法长度、错误时序、重复请求、旧连接消息和多连接隔离。增加真实原客户端的出站捕获及服务端到原客户端的反向验证。

```sh
set -eu
npm --prefix wave run test:wire -- --snapshot "$WAVE_SNAPSHOT" --stage W2
```

W2 门禁覆盖表中 1–4。W3 和 W4 覆盖 5–6 对应子集，W5 增加场景、蚁穴及 PvP。每阶段的 `test:wire` 同时跑字节夹具和该阶段的原客户端联机用例。报告保存收发消息、客户端是否完成操作、服务端结果和未确认字段。W6 汇总已支持流程的兼容结果。
