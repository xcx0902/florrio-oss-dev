# 当前 World PvP 代码的复用边界

**建议参考，按层复用。** 以提交 `2f90eed` 的源码为本次审计对象。优先移植纯基础设施和已验证的宿主、测试模式。涉及玩法语义、旧协议或玩家可见状态时，以 2022-10-30 原客户端和同期史料决定实现。Wave 独立构建，实际移植的最小代码单元随 `wave/` 保存。

| 类别             | 处理                                                          | 放行条件                                                             |
| ---------------- | ------------------------------------------------------------- | -------------------------------------------------------------------- |
| A · 直接复用候选 | 保留小型通用实现，只调整命名空间、依赖路径或独立构建接线      | 无旧游戏对象、旧线格式或目录依赖，在 Wave 的边界用例和独立构建中通过 |
| B · 抽取后适配   | 保留算法、测试结构或宿主模式，剥离 World PvP 的常量和数据契约 | 写清被替换的语义，验证输出、生命周期和失败路径                       |
| C · 重写或新增   | 以 10 月证据建立 Wave 自己的协议、玩法或状态                  | 原客户端端到端可用，已证实规则有测试，缺口可追溯                     |

## 落地顺序与验收

1. W0 从哈希、浏览器启动和归档探针开始。W1 先移植实际需要的向量、数值及有界字节操作。空间索引在生成或碰撞测试证明需要时接入。W2 再迁入通用宿主部分。优先打通原版进场，避免在确认原协议之前迁移整套引擎或宿主。
2. 每次移植在 `wave/REUSE.md` 登记源提交、文件及符号、类别、改动、依赖、Wave 测试 ID。先验证最小单元能独立编译，再接场景。任何依赖 `World`、现行协议生成物、旧目录或归档相对路径的移植按 B 类拆开。
3. A 类用数学、边界或工具测试验证等价。B 类用 Wave 的协议夹具、历史规则或真实客户端联机用例检验新行为。通过现有 World PvP 测试只能说明移植没有破坏已知通用契约，历史一致性仍以 Wave 证据为准。
4. W6 仅用 `wave/`、原件和同版资源构建并运行，核验复用台账与测试清单。现有 World PvP 可以照常构建运行，独立 Wave 不链接其整套 `engine_core`、现有 `florr_server` 或 TS 客户端。 [独立构建](06-verification-and-release.md#063-验证独立性与装配)
