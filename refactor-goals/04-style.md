# 04 — 写作、格式与可读性

## 目标

统一手写代码、测试、工具、配置和生成代码的写作方式。禁止把多个独立语句、分支或循环压缩到一行；禁止以生成文件、测试文件、热路径为由压缩逻辑。

## RF-S1：统一基础约定

建议采用与当前多数代码接近的格式，减少无关风格变化：

| 内容 | 约定 |
| --- | --- |
| 文件编码 | UTF-8、LF、文件末尾一个换行、清理行尾空格 |
| 缩进 | C++、TS、JS、JSON、YAML、CMake 使用 2 空格；禁止 Tab |
| 行宽 | 以 100 列为排版目标；不可拆分的路径、字符串、数据 token 可合理超出，不将其作为压缩代码豁免 |
| 大括号 | 声明和控制语句使用同一行起始风格；控制体始终使用大括号 |
| TS/JS | 单引号、分号、可换行结构使用尾逗号；类型导入明确标记 |
| C++ 类型 | `PascalCase`；枚举成员沿用 `kName` 风格 |
| C++ 函数和字段 | `snake_case`；常量使用 `kName`；生成 catalog 类型同步执行 |
| TS/JS 类型和函数 | 类型 `PascalCase`，函数/字段 `camelCase`；模块常量 `UPPER_SNAKE_CASE` |
| schema | JSON/YAML 属性采用当前 `camelCase` 约定，符号和类型按领域定义；不要求两种语言拼写完全一致 |
| 文件命名 | TS/JS 延续 `kebab-case`，C++ 延续 `snake_case`；只在原名含历史编号或意义不明时改文件名 |

当前 wire JSON 对象、框架接口和真实 ABI 名称有外部约束时保持约定拼写，在适配边界说明，不通过全项目强行改名制造协议变化。生成器负责 schema 到语言字段风格的稳定转换。

## RF-S2：明确禁止的压缩写法

1. 同一行多个独立赋值、调用、声明或断言。
2. 单行包含 `if/else` 与实际处理语句，或把完整循环和嵌套分支写成一行。
3. 有多个副作用的逗号表达式、连锁赋值和为缩短行数引入的条件表达式。
4. 用复杂三元嵌套、立即执行表达式或组合回调隐藏本应顺序展开的处理过程。
5. 模板用很长的单行字符串生成整段控制流，或生成函数、枚举、结构体时省略正常排版。
6. 用格式忽略指令包住逻辑代码；没有当前必要性的 lint disable、诊断屏蔽和 `[[maybe_unused]]`。

一行只有一个无副作用表达式的简单返回、属性 getter 和简短 lambda 可由统一 formatter 排版；复杂 getter 和 lambda 仍需展开。数据数组和几何坐标允许紧凑排列，但其中不能包含多步命令或控制流。

排版不能代替可读性整改。对 `s`、`g`、`f`、`c` 等难以理解的长作用域局部名改为 `snapshot`、`group`、`field`、`connection` 等具体名称；简单索引和数学坐标不机械拉长。guard clause 按失败原因分组，复杂条件提取有意义的判断或局部值。

## RF-S3：建立工具入口

计划新增 `.editorconfig`、Prettier 配置、ESLint 配置及 `.clang-format`，并提供以下脚本：

- `format`：只对明确纳入的手写文本文件执行格式修正；生成输出必须通过生成器更新。
- `format:check`：只读检查格式，覆盖手写代码和生成的 C++/TS。
- `lint`：检查可读性、无用代码、控制流和适当的语义规则。
- `check:refactor`：检查活动路径中的历史表示、编号式未知字段和业务裸 ID 等项目约束。

这些入口当前尚不存在。执行时锁定 formatter/linter 的准确版本、依赖及配置；记录 clang-format 的版本约束。生成、构建和验收阶段不在线下载工具，缺少工具时明确失败，不自动跳过。

按文件类型显式路由 formatter：TS/JS/JSON/YAML/HTML/Markdown 使用相应解析器，C++ 使用 clang-format，CMake 使用锁定版本的 CMake 格式工具。字体、图像、锁文件及其他机器数据不交给不匹配的解析器。不要用一个全目录通配符假设某个工具支持所有格式。

Prettier/clang-format 负责机械排版；ESLint/编译器及针对性 AST 检查负责多语句、控制流、无用参数等约束。单纯把 print width 调小不能保证没有压缩代码。C++ 无用参数和死成员的完整检查还需结合调用关系审阅，不能宣称一条 warning 已覆盖全部情况。

将这些检查接入现有 `tools/verification/gates.mjs` 的统一入口。`test:light` 等常用入口也应包含对应轻量检查或明确复用统一入口；不另起一个不参与验收的“可选规范检查”。新增脚本、配置和生成所需工具身份纳入适用的构建/验证输入。

## RF-S4：让生成结果始终可读

优先整改 `tools/schema/multiplayer.mjs` 的 `rw`、records/enums/message 编码模板，以及 protocol/catalog 类型和初始化列表模板：

1. 将可读性差的多分支生成逻辑拆成按字段类别命名的少量函数；每个函数有实际职责。
2. 生成正常分行的函数、结构体、枚举、错误检查和循环。
3. 在内存中对生成文本使用锁定版本的格式化流程，**先格式化最终内容，再计算 bytes/SHA-256 和输出清单，最后写入**。
4. C++ 与 TS 的输出遵守各自同一份仓库配置。所需 formatter 作为生成前置依赖记录并检查；不能在生成完成后另行格式化以致清单失真。
5. `--check` 执行相同纯生成与格式流程，但不写文件；校验失败不得部分修改原输出。
6. 二次生成内容完全相同；格式检查不得用 `prettier-ignore` 或 `clang-format off` 绕过生成逻辑。

## RF-S5：分离格式和语义变更

先形成可单独审查的格式批次，再做字段、协议和接口调整。格式批次不提取常量、不删除语句、不合并计算、不调整分支顺序，也不改变捕获和析构作用域。

生成器改排版导致生成文件和哈希更新是预期结果；更新清单后核对生成代码的结构和行为。后续语义批次保持 formatter 通过，不再把大段手工排版混入逻辑差异。

对几何精度、随机抽取、异步等待、异常清理和 C++ 临时变量生命周期保持特别关注。为了加大括号而改变作用域时必须检查局部对象析构时机。

## 输出与验收

全部活动手写代码和生成代码通过格式检查；无压缩控制流；工具版本可复现；校验入口真正进入统一验收。人工抽查服务端状态流转、客户端网络接收、schema 模板及测试辅助函数，确认可读性实际改善。
