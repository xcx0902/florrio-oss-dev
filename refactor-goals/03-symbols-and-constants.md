# 03 — 业务标识与常量

## 目标

业务代码以名称表达花瓣、生物、稀有度、动作、协议字段、容量和规则。数值仍由权威来源定义，不能在各语言、各模块重复维护。

## RF-L1：建立稳定且唯一的 catalog 符号

在现有花瓣和生物身份记录中加入显式、稳定的 `symbol`；继续由 `petals.json`、`entities.json` 各自拥有对应数值 ID，不新增一套手写 ID 对照表。

校验规则：symbol 非空、在所属域中唯一、可转换为目标语言标识、无关键字冲突或转换后重名；type ID 的当前范围、稀疏 ID 和交叉引用规则继续生效。显示名变化不能自动改变 symbol。

同名不同稀有度的 Rose、Egg、Web 等应使用明确成员名；Centipede 头与节也要区别命名。推荐如 `RoseUnusual`、`RoseEpic`、`CentipedeHead` 等，最终对照当前身份和用途确定。不能生成 `Rose15` 或仅靠数组位置消除歧义。

由同一生成器输出：

| 领域 | C++ | TypeScript | 数值来源 |
| --- | --- | --- | --- |
| 花瓣身份 | `enum class PetalId` | `PetalId` 常量对象及值类型 | `schema/catalogs/petals.json` |
| 生物身份 | `enum class SpeciesId` | `SpeciesId` 常量对象及值类型 | `schema/catalogs/entities.json` |
| 当前使用的稀有度 | 具名枚举/常量 | 具名常量及类型 | 统一当前 catalog 稀有度定义，避免从显示名称反推 |

建议新增生成输出 `engine/include/engine/catalog/ids.hpp` 和 `client/src/schema/catalog-ids.ts`，同步注册 `outputs.mjs`、输出清单和相关身份计算输入。文件名是计划，不代表已创建。若现有生成文件更适合承载，执行时可以合并，但唯一来源原则不变。

不使用 TypeScript `const enum` 作为跨模块导出的默认方案，保持与当前 `isolatedModules` 配置及运行时测试导入方式一致。

## RF-L2：逐域替换业务调用

1. 引擎 sim 的花瓣效果、孵化、被动能力、轨道、死亡和掉落分支。
2. 引擎出生、AI、移动和族群判定中的生物 ID。
3. 客户端世界绘制、shape、动画、菜单预览、tooltip、loadout 和测试工具中的身份值。
4. 当前测试里的业务场景使用具名身份；wire 边界、稀疏 ID、未知 ID 和故障输入测试保留解释清楚的原始数字。

API 边界若仍需数值，使用显式转换，不在每个调用处添加难读的强制转换链。花瓣 ID 与生物 ID 即使数值相同也不能互换；C++ 优先由类型区分，TS 至少在函数参数、命名和生成入口区分。

对族群的判断要表达成员关系。用 `isAntSpecies`、`isCentipedeSpecies` 或固定集合替代编号区间、减去某 ID 推算种类、手工排除中间编号等逻辑。不能把数字端点换成常量后继续假设 ID 连续。

## RF-L3：统一协议标识

从 `schema/protocol.yaml` 和 `schema/multiplayer.yaml` 生成并使用：

- 当前有业务读取的 snapshot field、组件及组件存在性标志。
- 输入和事件 opcode、输出类型、多人消息类型、错误码和动作标志。
- 字段数、包/数组上限、slot/instance sentinel、量化上限、component mask 等真实协议约束。

优先复用已有生成枚举。当前已有 `InputOpcode`、多人枚举和各类 LIMITS，不能重新手写一套等价值常量。现有枚举仍承载历史实现编号时，按 [01](01-fields.md) 和 [02](02-product-semantics.md) 清理，不能仅以“有枚举”判定合格。

协议组标识必须是当前组件语义，不能用 `Offset116`、`Minus16` 等名称包装旧内存布局。

## RF-L4：整理容量、计时、物理与 UI 规则

按含义而非数值相等归类：

| 类型 | 放置方式 | 代表事项 |
| --- | --- | --- |
| 跨端契约与玩法共享规则 | 现有 schema 的唯一归属点，必要时新增明确 schema 定义并生成两端视图 | 50ms tick、槽位上限、实例数、解锁等级 |
| catalog 中每种物品不同的属性 | 对应 catalog 记录 | 治疗量、充值时间、碰撞/绘制/标签尺寸 |
| 单模块算法参数 | 模块级 `constexpr`/`const`，含单位说明 | 插值收敛、碰撞阈值、动画持续时间 |
| 有名称的一组 UI 布局规则 | 当前布局模块或有类型的配置对象 | 卡片尺寸、间距、边距和层级 |
| 特定形状的路径点和颜色数据 | 就近保留结构化几何/调色数据 | 控制点、离散采样、图形轮廓 |

不建立装下全部常量的巨型 `constants` 模块。同值的“背包槽数”“死亡保留条目上限”和“协议字段宽度”若职责不同，应分别命名。

有业务意义的 0/1 也要处理，例如 `None`、攻击 bit、空槽与无效 slot；普通循环初始值、加一和纯数学运算不要求机械提取。几何路径字面量可作为明确的数据块保留，但其中的业务身份、动画时长、缩放规则和重复尺寸仍须命名。

同样审阅重复的业务字符串：状态、模式、消息类别等优先使用既有类型或统一常量；文案、错误说明和 catalog 显示文本保留在各自权威数据源，不为每个单次字符串另建无意义常量。

提取数值必须保持类型和精度：`float/double/f32`、整数宽度、fround 次数、运算顺序、十六进制精确常量与单位不随手改写。诸如 `1e-7` 应说明是位置阈值还是数值安全阈值，再决定本地常量归属。

## RF-L5：检查与验收

建立按上下文检查的规则：重点检查身份分支、接受 ID 的调用参数、业务数组、bit 运算和协议字段访问；不对所有数字实施无差别禁用。规则与语义审阅结合，无法自动识别的场景必须逐模块核对。

验收要求：

- 同一身份只有一处数值定义，两端生成值一致；显示名重复不引起符号冲突。
- 常规业务代码中的花瓣/生物身份、动作和协议字段不再裸写数字。
- 族群逻辑不依赖 ID 连续性；未知和稀疏 ID 测试仍有效。
- ID、wire 字节、稀有度、概率、动画和数值计算结果保持不变。
- 添加、删除、重命名 symbol 或产生语言标识冲突时生成器正确校验；生成、二次生成和只读 check 一致。
