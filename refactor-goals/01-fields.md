# 01 — 字段删除与语义命名

## 目标

消除按旧偏移或未知内容命名的字段。无实际用途的字段从整条生产链删除；有用途的字段使用当前业务含义、物理意义或明确的协议职责命名。

## RF-F1：建立字段读写和数据流清单

逐个检查 schema 属性、C++ 成员、TypeScript interface/状态、生成类型和测试辅助结构，不局限于 `flags92` 和 `opaque100`。

1. 从定义追踪默认值、赋值、拷贝、计算读取、序列化、持久化和展示。
2. 区分“生成器把值拷贝到另一个表”与“产品使用该值决定行为”。纯搬运不是业务用途。
3. 区分测试只检查存储值与测试实际检查行为。仅存在前一种测试时，不能以该测试为由永久保留无用字段。
4. 对 ABI、wire、反射、对象展开、JSON、聚合初始化、类型布局和 diagnostics 进行额外核对，避免漏掉间接访问。
5. 每个结论标记为删除、保留并改名、与其他字段合并，或者待核实。待核实项不能在阶段结束时自动算作完成。

## RF-F2：优先删除无用 catalog 和出生字段

优先核查 F01/F02/F04：`opaque100/104/108/110`、`flags92`/`component_flags92`、catalog 的 `physicsFlag48`。

证实无业务读取后，按以下顺序在一个完整修改批次中处理：

1. 删除 schema 输入中的属性和相应必填校验。
2. 删除 `tools/schema/catalogs.mjs` 中 join、类型、初始化列表及输出模板中的属性。
3. 删除运行时成员、无效赋值、拷贝和诊断暴露；检查聚合初始化位置，防止后续字段错位。
4. 删除仅检查被删除字段数值的断言；保留或改写为半径、碰撞、掉落等可观察行为断言。
5. 重新生成所有输出和 `generated-outputs.json`，同步当前 catalog 文档。
6. 在活动数据和代码中复查，不能剩下空字段、占位列、废弃别名或兼容 setter。

catalog 的 `physicsFlag48` 与运行时 `physics_flag48` 分开决定：前者当前未见读取，后者有明确碰撞用途，不能连带删除。

## RF-F3：为有效状态建立可解释的类型

| 现有表示                                                    | 目标方向                                                            | 命名证据要求                                     |
| ----------------------------------------------------------- | ------------------------------------------------------------------- | ------------------------------------------------ |
| `entity_flags`、`world_flags`、`flags93/95`                 | 有明确职责的标志集合及具名 bit；必要时在 wire 边界保留原始字节      | 每一位列出设置者、判断者、序列化位置以及当前作用 |
| `physics_flag48`                                            | 如 `uses_mass_weighted_response` 的物理含义名称，最终按全部读取确认 | 质量加权与全重叠推开的各条分支行为               |
| `physics_flag50`                                            | 根据 Web 标记是否应跳过接触响应确定状态名                           | 创建、重复接触、死亡和清理路径                   |
| `activity_flags`、`player_expression`、输入按钮等其他位集合 | 具名 action/appearance/activity 标志                                | 不同域即使 bit 相同，也不能混为一套枚举          |
| `componentDrawCount`                                        | 描述实际掉落抽取次数的名称                                          | RNG 调用次数、循环顺序和结果用途                 |
| `HitEvent::refcount`                                        | 删除重复状态；如确有独立职责则按该职责命名                          | 与 `count` 的所有更新与消费关系                  |

以上英文名称是提议，不是已验证的最终名称。不得仅凭旧偏移或数值猜测位含义。无法对应业务意义但确须保留的协议位，应在边界明确表示为保留位及其协议约束，不能继续混入领域状态。

命名要求：bool 表达明确判断，计时字段注明 `_ms`/`Ms` 或 `_tick`/`Tick`，比例说明范围，原始协议值与领域值分开。C++/TypeScript 拼写分别遵守 [04](04-style.md)，共享含义以 schema 定义为准。

## RF-F4：替换花瓣轨道函数编号

当前编号链同时承载“是否为治疗花瓣”和“每次治疗多少”。目标应将行为和数值参数分开：

- 在 combat schema 中定义当前花瓣行为类型，以及该类型确实需要的治疗量、延时等参数。
- 复用已有 `OrbitProfile` 表达环绕半径轨迹；如它不能表达治疗生命周期，增加职责明确的 `PetalBehavior`，不要把两个概念揉在一起。
- `PetalOrbitState` 使用强类型行为；如果可以安全从不可变 catalog 查询，则不再额外缓存等价字段，具体以生命周期和开销判断。
- `petals.cpp` 依据行为和具名参数决定治疗，不再比较函数编号。
- 同步删除 `orbitFunctionIndex`、`orbit_function`、`is_rose_orbit_function` 和相关校验、生成、断言、注释。

验证必须覆盖三种当前 Rose 治疗量、严格的一秒启动条件、治疗阻断、主人死亡、十步治疗状态、花瓣消耗与充值，以及普通轨道、Wing 波动、Egg、投射物和共享轨道未被误归类。具体行为取当前代码和现行测试，不从归档恢复。

## RF-F5：替换 AI 历史回调编号

沿用现有攻击分发职责，将 `AiState` 中的整数改为当前攻击行为类型。`configure_hornet`、AI 冷却判断及分发入口直接使用该类型。

现有 `AttackCallback` 虽有枚举名，但成员数值仍为历史编号 74。先确认该值没有进入当前 wire、存储或公开 ABI；没有外部约束则移除这层编号。未知行为输入的处理只在真实需要的边界保留，不为测试构造任意 callback id 而维持整套历史分发模型。

## 输出与验收

- 全量字段处置表中无未决项；删除与改名都有消费者依据。
- schema → 校验 → 生成 → 引擎/客户端 → 测试/文档整条链完成迁移。
- 保留标志无裸 bit 运算，序列化字节与实际行为保持一致。
- 没有以 `_unused`、`reserved92`、`legacyFlags`、`callback665` 等形式保留旧意义不明状态。
- 按 [08](08-verification.md) 完成 schema、引擎、跨端和相关客户端验证；catalog hash 变化作为元数据变更记录，双方必须一致。
