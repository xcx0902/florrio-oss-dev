# M03：PVP、花瓣与玩法归属

状态：未开始。依赖：M02。产出：两个玩家在同一个原生 World 中可以完整对战，经验、治疗、掉落、死亡和重生按真实玩家结算。

## 03.1 修改范围

重点审查 `sim/player.cpp`、`player_loadout.cpp`、`petals.cpp`、`petal_lifecycle.cpp`、`petal_effects.cpp`、`passives.cpp`、`pets.cpp`、`combat.cpp`、`damage.cpp`、`death.cpp`、`loot.cpp`、`targeting.cpp`、`species_attacks.cpp` 和 `model/entity_relations.cpp`。

复用现有实体池、接触求解、effect、目录与花瓣数值；不创建只给联网使用的第二套战斗系统。新增 `engine/tests/unit/test_multiplayer_combat.cpp` 与 `test_multiplayer_lifecycle.cpp`。

## 03.2 先解决实体归属

1. 明确区分物理 owner、controlling root 与击杀归属。现有 `controlling_root()` 决定同一控制体免伤；`owning_player()` 查询攻击所属玩家；两者不能合并成一个布尔函数。
2. 给玩家 body、花瓣、宠物及其投射物写入可查询的 PlayerId 归属。对延迟伤害额外保存创建时的来源身份，避免攻击实体或身体消失后错误归给复用槽位的新玩家。
3. 归属保存 PlayerId + 必要的来源 handle/代际，不保存指向 PlayerState/Entity 的裸悬空指针。玩家 ID 在本房间不复用；已离场身份的历史伤害不得发给另一个新玩家。
4. owner 链无效、循环、尸体、换代或控制体退出都有确定行为。攻击者不能靠传入任意 PlayerId 改写归属，来源由服务端实体创建流程设置。
5. 把玩家昵称作为该玩家公开资料；killer name 从真实来源查询/快照保存，不再从 `world.player_name()` 读取全局昵称。

## 03.3 逐系统迁移步骤

| 系统 | 执行动作 | 关键断言 |
| --- | --- | --- |
| 装备交换/丢弃 | 命令带显式 PlayerId，校验槽位和当前物品 | A 操作不拆掉 B 的花瓣 |
| 轨道与充能 | orbit phase、实例句柄、pending timer 属于各自 loadout | A 花瓣破坏仅充能 A 的对应实例 |
| 攻击/防御 | 每个 PetalOrbitState 使用所属玩家输入 | A 防御不收缩 B 的花瓣 |
| Rose/Leaf/被动 | 治疗与生命上限查询所属玩家和真实目标 | A 的治疗不作用于 B |
| Peas/Stinger | 发射/延迟发射携带来源身份和归属 | 母体消失后不串号、不重复发射 |
| Egg/宠物 | 孵化继承 owner 与 PlayerId，目标资格使用控制根 | 自家宠物不攻击自己，对手可被攻击 |
| 毒/反伤/区域效果 | 每个 effect 保存真实来源，死亡链幂等 | 杀人归属、反伤和 DOT 不用当前玩家兜底 |
| AI | 搜索所有合格玩家/宠物，沿用稳定候选顺序 | 怪物能发现 B，A 死亡后能重新选目标 |
| 拾取 | 查询所有合格玩家，按距离/PlayerId 选唯一接收者 | 同一 drop 只增加一次库存 |
| 经验/升级 | `award_player_experience` 接收目标 PlayerId | A 击杀怪物只升级 A |
| 死亡 | 对死亡目标的档案/装备/子实体执行处理 | A 死亡不销毁 B 的花瓣 |
| 重生 | 从该玩家保留资料生成新 body | 新 handle、同 PlayerId、无重复掉落 |

执行时先改显式参数，再补归属回归，最后删除旧隐式路径。特殊花瓣按现有目录能力逐项覆盖，不能仅以 Basic 花瓣通过就宣布全部完成。

## 03.4 首版 PVP 规则与数值

1. 模式为 FFA，不增加队伍系统。相同控制根保持现有免伤；不同玩家之间使用现有碰撞/伤害规则。
2. 修复 `level_damage_scale()`：双方等级分别从各自 PlayerState 读取，保留当前函数的系数公式及仅针对玩家本体接触的适用范围。测试等级 1/5/6/10 与双方互换，明确低等级本体接触可能无伤；不要把「无法互伤」误判为网络失败。
3. 花瓣接触、宠物、投射物、毒和反伤保持各自现有规则，不把本体系数顺手扩展到所有攻击。
4. 怪物击杀经验发给实际攻击所属玩家。首版不新增玩家击杀 XP 或金币；若以后增加，作为独立玩法变更。
5. 同 tick 双方死亡保持已有接触处理顺序，死亡处理具有一次性标记；不为让测试对称而重排求解器。
6. 出生位置沿用地图与等级带规则，检查所有存活玩家和相关占位实体。找不到安全出生点时返回明确失败，不能重叠出生或卡住整个 tick。
7. 断线期间攻击/防御过 TTL 后中立，身体仍可受伤；保留期到期走离场清理，不能再次触发已经处理过的死亡奖励。

## 03.5 死亡、拾取与重生的事务边界

死亡过程必须一次完成：标记 death_processed → 保存该玩家 killer/death 元数据 → 按既有 loot 算法计算保留物 → 创建地面掉落 → 处理其子实体 → 设置尸体到期。快照发布与连接掉线都不能再次调用这段结算。

拾取过程必须一次提交：选定合格接收者 → 校验库存仍有空间 → 写入其库存/装备 → 将 drop 标记为已收取并绑定接收者 → 产生事件。争抢失败者不产生视觉转移；完成前接收者死亡/离场时，按既有转移语义明确取消或完成，不能转交一个已复用的 handle。

重生校验同时考虑尸体窗口和出生冷却。等待期间服务端继续模拟其他玩家；客户端只显示返回的权威可重生 tick，不能靠按钮次数缩短冷却。

## 03.6 测试矩阵

- `A petal → B body`、`B petal → A body`、本体对撞、双方花瓣对撞：血量/归属正确。
- 自家花瓣/宠物/投射物不伤害本玩家；普通野怪之间保持既有控制根语义。
- A/B 的装备、Rose/Leaf、特殊充能、攻击/防御和区域限制彼此独立。
- A 的宠物/投射物/DOT 击杀 B 后 killer name 正确；来源实体销毁或槽位换代不改写来源。
- A/B 同时接触一个 drop：只发给确定的胜者；等距情况可重复得到同一结果。
- A 击杀怪物只获得 A 的经验；B 的等级、库存和血量上限不跟随变化。
- A 死亡期间 B 继续移动/战斗；A 的尸体删除后死亡资料仍可读取。
- A 重生后 PlayerId 不变、body handle 改变；旧身体和旧输入不能控制新生命。
- 连续 100 次可控死亡/重生，检查实体、花瓣实例、effects、deferred launches 无持续残留。
- 两个房间交替执行同样场景，事件/分数/随机数不串房。
