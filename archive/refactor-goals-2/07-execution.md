# 07 — 执行顺序与交付方式

本文件说明以后获准实施时如何推进。本次未执行以下任一步骤，也未安装工具、修改配置或运行验证。

## 阶段总表

| 阶段         | 具体范围                                                | 进入条件 | 阶段输出                   | 退出条件                                 |
| ------------ | ------------------------------------------------------- | -------- | -------------------------- | ---------------------------------------- |
| P0 基线      | 当前源码、字段/参数/调用清单、验证环境                  | 开始实施 | 当前基线与完整处置表       | 基线问题和已有失败已明确，保护场景可复现 |
| P1 格式      | 配置、手写代码、测试、生成模板和输出                    | P0       | 独立格式批次及必需工具入口 | 格式和结构检查通过，行为未变             |
| P2 标识      | catalog symbols、ID、协议字段、bit、容量与规则常量      | P1       | 唯一来源和两端生成符号     | 数值不变、无冲突、常规业务裸 ID 清除     |
| P3 字段/行为 | 无用字段、有效 flags、花瓣行为、AI 攻击行为             | P2       | 字段处置、强类型行为和参数 | 全链迁移及相关回归通过                   |
| P4 协议模型  | constructor/offset、dense 组、snapshot 投影、多人公开组 | P2、P3   | 当前协议内部表示           | 字节与事务行为不变，历史布局清除         |
| P5 接口      | 未使用参数、默认值、内部调用链                          | P3、P4   | 精简签名和全部调用迁移     | 类型/编译及相关行为验证通过              |
| P6 去重/文档 | 重复 factory、清理流程、镜像状态、测试 helper、当前说明 | P3–P5    | 单一职责实现与当前文档     | 无未决死代码项，独立验证能力保持         |
| P7 验收      | 全量规范检查、构建、跨端、浏览器、性能、干净副本        | P1–P6    | 最终差异、证据和完成清单   | 六项要求全部通过，失败和跳过项为零       |

模块注释随对应阶段一起改写，P6 做最终全局检查。阶段按顺序推进，不一次性同时改全项目后才尝试构建。

## P0：先固定当前事实

1. 重新读取 Git 状态、适用约定和 HEAD；若基线与本计划不同，增量核对问题清单。
2. 检查 Node、CMake、C++ 编译器、Emscripten、Chromium 等环境，读取已有版本约束；如需要新增格式工具，先决定准确版本及离线可用方式。
3. 以 `tests/product-tests.json`、`tools/verification/gates.mjs` 和 `generated-outputs.json` 为当前清单，不沿用旧文档中的数量。
4. 执行当前 schema 检查和全量验收，记录输入身份、工具版本、失败情况和 runId。已有失败先明确原因，不能把旧报告当成新基线。
5. 完成字段、参数、死代码和业务字面量处置表；对文本搜索不能覆盖的导出、聚合初始化、对象展开、间接调用作补充检查。
6. 确认当前 wire 手写向量、native 跨端、Rose/投射物/孵化、出生随机顺序和多人生命周期测试是否足以保护本次改动。只补足真正缺失的风险场景，不为简单改名机械增加测试。

产出可放在本目录的后续执行记录或专门 evidence 文档中；状态仅在命令实际完成后更新。

## P1：形成独立格式批次

1. 新增并锁定 [04](04-style.md) 中的工具与格式配置。
2. 先让生成器输出正常排版的 C++/TS，并在写入和哈希计算之前完成格式化。
3. 重新生成输出和清单；随后格式化手写代码、测试、工具和配置。
4. 接入只读检查和统一验收，核对新增工具和配置进入适用的身份计算。
5. 审查格式差异，确保没有混入字段删除、公式简化、顺序调整和参数精简。

该批次通过后再进行语义修改。后续每批次都保持相同格式，不叠加第二套风格。

## P2–P4：按数据流迁移

每个语义批次采用同一顺序：

1. 修改权威 schema/领域类型及对应校验。
2. 修改生成器的类型和数据输出；需要新增输出时登记输出构建入口及清单。
3. 更新 C++/TS 生产者、消费者及调用边界。
4. 更新当前测试的输入和断言；手写协议期望值保持独立。
5. 在内存完整校验后生成所有输出；运行只读 schema check。
6. 运行该批次所需构建和回归；定位失败，不以批量重录 expected/golden 解决。
7. 删除过渡适配和旧名字；搜索复查，检查 metadata、数据字段、注释和测试名是否仍引用旧表示。
8. 更新对应规范及处置表。

建议细分成可审查的批次：

- P2a：catalog symbol、PetalId、SpeciesId；P2b：协议字段、标志与共享规则。
- P3a：无消费 catalog/出生字段；P3b：有效 flags 命名；P3c：Rose 与 AI 行为替换。
- P4a：字段/组件 schema 与生成器；P4b：引擎、客户端和多人公开字段完整迁移。P4a/P4b 可以分开审查，但交付边界必须可构建、无永久旧接口。

## P5–P6：接口与职责收敛

先精简参数，稳定各职责的真实输入，再合并重复流程。一个批次只处理一个可解释的职责，例如出生 factory 或花瓣解绑，不把 UI、网络和出生逻辑混在同一语义差异中。

针对 snapshot，先完成权威表示的迁移，再删镜像状态和 fallback。针对测试，先确认独立验证职责，再提取测试内部 helper。

最后重写当前说明文档，核对代码链接、符号和命令入口；历史文档标识清楚，归档保持不变。

## P7：交付与验收

1. 对六项要求分别复审，关闭每一条处置表记录。
2. 运行最终轻量检查和既有全量验收；验证报告必须对应最终源码和最终产物。
3. 使用不含归档、Git、已有编译产物及依赖目录的干净副本，安装锁定依赖并重新构建、验收，证明没有恢复历史依赖。
4. 检查最终 Git 差异：只包含必要源码、配置、schema、生成输出、测试与当前说明；没有混入本地构建、缓存和旧报告。
5. 交付变更摘要、字段/接口迁移表、验证命令与结果、剩余限制。任何未完成要求都应明确列出，不能以搜索无命中替代验收。

本计划不包含推送、合并、部署或发布。是否形成 Git 提交及其划分属于将来实施的交付安排，本次没有执行。

## 停止、修正与回退条件

- 字段或标志无法解释：补查当前生产/消费关系，不猜名、不删除、不假装完成；其他独立工作仍可推进。
- 发现真实协议、存储或玩法需要变化：从规范化批次拆出，保留当前契约，单独说明需要的产品决策。
- 测试出现与格式无关的差异：先定位作用域、默认值、计算顺序和状态清理，不批量接受新期望。
- 工具不可用：报告具体缺失条件；不能静默跳过规范检查或把没有运行写成通过。
- 回退采用最近一个独立批次的可审查差异，schema、生成器、输出和消费者一起回退；不恢复归档实现，不覆盖实施期间已有用户修改。

代码身份、生成文件内容和 catalog hash 可能因规范化发生合理变化；它们不要求与旧提交相同。协议行为和玩法结果的变化必须另有明确理由，不能借元数据变更一并接受。
