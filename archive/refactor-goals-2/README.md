## 实施边界

1. 以当前项目的行为、协议、测试和产品约定为准；不读取归档实现来补充命名或恢复旧行为。
2. `archive/` 保持原样；`build/`、`dist-next/`、`reports/`、`release/`、依赖和缓存不作为手写代码整改对象。未来验证产生的文件按既有规则管理。
3. 不改变花瓣和生物 ID 的数值、协议字节格式、物理公式、随机序列、事件顺序、存档和设置语义。发现现有功能缺陷时单独记录，避免混入规范化修改。
4. schema 或生成器的修改必须连同生成输出及清单一起完成，不直接手改生成文件。
5. 不靠更换 `opaque` 前缀、给旧函数编号起枚举名、保留过渡别名或关闭检查来宣称完成。
6. 历史记录可以保留历史事实；当前规范、代码和注释必须独立说明当前行为。具体划分见 [02](02-product-semantics.md)。

## 推荐执行路线

`P0 基线与清单 → P1 格式体系 → P2 语义标识 → P3 字段与行为 → P4 协议内部表示 → P5 接口精简 → P6 去重与文档 → P7 全量验收`

这是一条有先后依赖的路线：先建立可读和可检查的代码，再做符号替换，随后删除字段和历史表示，最后处理跨模块重复。每阶段必须形成可独立审查的差异并通过对应检查，不能仅以“下一阶段会修复”为由放行。

完成度以清单及当前验证证据为准，不以删掉的行数、搜索命中减少数或旧报告中的通过数量衡量。
